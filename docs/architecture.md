# Архитектура проекта

Этот документ описывает текущую структуру проекта без предложения обязательного
рефакторинга. Его цель - помочь разработчикам и ИИ-агентам быстрее понять, где
находятся основные части системы и какие границы ответственности уже сложились.

## Назначение проекта

Проект представляет собой образовательную платформу на FastAPI с серверным
рендерингом Jinja-шаблонов. В системе есть публичные страницы, каталог курсов,
кабинеты студентов, преподавателей, организаций и администратора, групповые
занятия, уроки, материалы, домашние задания, журнал, платежи, уведомления,
профили организаций и пользователей.

## Общая структура директорий

```text
.
├── app/                 # Python-код приложения
│   ├── models/          # SQLAlchemy-модели
│   ├── routers/         # FastAPI-роутеры
│   └── utils/           # Вспомогательные технические и прикладные функции
├── alembic/             # Миграции базы данных
├── config/              # Файлы окружения
├── data/                # Runtime-данные: логи, backup-заглушки
├── docs/                # Документация проекта
├── scripts/             # Вспомогательные скрипты разработки
├── static/              # CSS, JS, изображения, загрузки и публичные ассеты
├── templates/           # Jinja2 HTML-шаблоны
├── tests/               # Место для тестов
├── main.py              # Точка входа FastAPI-приложения
├── requirements.txt     # Python-зависимости
└── alembic.ini          # Конфигурация Alembic
```

Служебные директории вроде `.git/`, `.venv/`, `__pycache__/` и `.vscode/` не
являются частью архитектуры приложения.

## Ключевые точки входа

- `main.py` создает экземпляр `FastAPI`, подключает middleware, статические
  файлы, роутеры, обработчики ошибок, главную страницу, service worker и startup
  hook для Alembic.
- `app/config.py` загружает переменные окружения и предоставляет настройки
  приложения.
- `app/database.py` настраивает SQLAlchemy engine, session factory, `Base` и
  dependency `get_db`.
- `app/ui.py` создает общий экземпляр `Jinja2Templates` и регистрирует фильтры и
  globals для шаблонов.
- `app/dependencies.py` содержит общие проверки пользователя, ролей и доступа.
- `app/course_flow.py` содержит вспомогательную логику прохождения обычных
  курсов.

## Директория app

`app/` содержит основной backend-код. Сейчас проект использует практичную схему
`routers + models + utils`, отдельного слоя `services` в проекте нет.

### app/routers

`app/routers/` содержит FastAPI-маршруты. Роутеры отвечают за HTTP-входы,
получение зависимостей, чтение форм, проверку доступа, подготовку контекста для
шаблонов и возврат HTML/API-ответов.

Основные роутеры:

- `auth.py` - регистрация, логин, logout, pending-страницы.
- `users.py` - маршруты dashboard для студентов и преподавателей, уведомления
  студентов.
- `courses.py` - каталог, публичная страница курса, управление курсом,
  материалы, quiz URL и API курса.
- `lessons.py` - обычные уроки курсов.
- `modules.py` - модули обычных курсов.
- `groups.py` - группы, групповые уроки, материалы, домашние задания, журнал,
  платежи, словарь и связанные student/teacher views.
- `organization.py` - кабинет организации, преподаватели, студенты, заявки,
  объявления, профиль организации и публичная страница.
- `admin.py` - административные страницы и действия.
- `pages.py` - статические и поисковые страницы.
- `profile.py` - профиль пользователя.
- `comments.py`, `reviews.py`, `push.py` - комментарии, отзывы и push API.

Крупные роутеры, которые требуют особенно осторожной навигации:

- `app/routers/groups.py` - самый крупный файл; объединяет несколько доменных
  областей группового обучения.
- `app/routers/organization.py` - объединяет кабинет, публичный профиль,
  membership flows и объявления организации.
- `app/routers/courses.py` - объединяет публичные страницы, управление курсом,
  материалы, изображения и API.
- `app/routers/auth.py` - содержит большой workflow регистрации разных ролей.
- `app/routers/admin.py` - содержит административные действия и каскадные
  операции удаления.

Эти файлы являются чувствительными зонами. Их не следует рефакторить целиком в
рамках обычных задач: изменения должны быть точечными, с заранее понятной
границей и проверкой затронутого workflow. Массовый перенос кода из этих
роутеров допустим только как отдельная архитектурная задача.

### app/models

`app/models/` содержит SQLAlchemy-модели, разложенные по доменам:

- `user.py` - пользователи и роли.
- `course.py`, `module.py`, `lesson.py`, `material.py`, `progress.py` - обычные
  курсы и прохождение.
- `group.py` - группы, групповые уроки, участники, журнал, домашние задания,
  платежи и связанные сущности.
- `organization.py` - организации, связи с преподавателями и студентами,
  объявления.
- `quiz.py`, `vocabulary.py` - тесты и словарные задания.
- `comment.py`, `review.py`, `contact.py`, `category.py` - дополнительные
  сущности платформы.

Модели являются схемой домена и базой для миграций Alembic.

### app/utils

`app/utils/` содержит вспомогательные модули. Часть из них является техническими
helpers, часть уже содержит прикладную логику:

- `security.py` - очистка HTML.
- `uploads.py` - безопасные имена файлов и валидация загрузок.
- `csrf.py` - CSRF token helpers и middleware.
- `rate_limit.py` - объект rate limiter.
- `image.py` - операции с изображениями и Cloudinary.
- `push.py` - отправка push-уведомлений.
- `announcements.py` - выборка видимых объявлений.
- `group_analytics.py` - построение аналитики групп и студентов.

Текущее состояние: `utils` используется и для технических функций, и для
прикладных сценариев. При дальнейшем развитии желательно держать в `utils`
только функции без собственной доменной ответственности.

Новые доменные функции не стоит автоматически складывать в `utils`. Если функция
знает о сценариях продукта, ролях, статусах, связях моделей или меняет состояние
домена, ей больше подходит будущий доменный слой, например `app/services`.

## Где находится бизнес-логика сейчас

Отдельного слоя `app/services` в текущей структуре нет. Бизнес-логика сейчас
распределена так:

- в роутерах: проверки ролей, создание и изменение сущностей, каскадные действия,
  подготовка данных для страниц, загрузки файлов, уведомления;
- в `app/utils`: загрузки, push-уведомления, объявления, аналитика;
- в `app/course_flow.py`: логика прохождения обычных курсов;
- в моделях: связи, constraints и базовое описание доменных сущностей.

Это фактическое устройство проекта на момент написания документации. Документ не
выполняет и не требует рефакторинг.

При добавлении новой сложной доменной логики предпочтительно не увеличивать
роутеры, а выносить такую логику в будущий `app/services` или другой явно
названный доменный модуль. Старый код не нужно переносить массово без отдельной
задачи, потому что текущие крупные роутеры связаны с несколькими пользовательскими
workflow.

## Директория templates

`templates/` содержит Jinja2-шаблоны. Структура организована по зонам продукта:

- `templates/base.html` - общий layout.
- `templates/pages/` - главная, поиск и информационные страницы.
- `templates/auth/` - login/register/pending.
- `templates/dashboard/` - кабинеты студента и преподавателя.
- `templates/courses/` - страницы курсов.
- `templates/lessons/` - страница урока.
- `templates/groups/` - страницы групп, уроков, журнала, платежей, домашних
  заданий и словаря.
- `templates/organization/` - кабинет и публичные страницы организаций.
- `templates/admin/` - административный интерфейс.
- `templates/profile/` - профили пользователей.
- `templates/errors/` - страницы ошибок.
- файлы вида `templates/_*.html` - общие partials/macros, например карточки,
  sidebars и вспомогательные компоненты.

Некоторые шаблоны являются крупными и содержат много разметки конкретного
workflow. При изменениях в них важно сначала определить доменную область и
связанный роутер.

## Директория static

`static/` содержит публичные ассеты:

- `static/css/` - стили приложения.
- `static/js/` - клиентские скрипты.
- `static/js/i18n.js` - переводы интерфейса.
- `static/images/` - изображения проекта, включая логотипы.
- `static/favicon/` - favicon и app icons для браузеров и устройств.
- `static/icons/` - дополнительные иконки интерфейса, если они используются
  отдельно от favicon-набора.
- `static/uploads/` - пользовательские или runtime-загрузки, доступные как
  static files, если конкретный workflow сохраняет файл локально.
- `static/materials/`, `static/documents/` - дополнительные публичные файлы и
  документы.

Пользовательские загрузки могут храниться в подпапках `static/uploads/`, а часть
файлов и изображений также может отправляться во внешнее хранилище Cloudinary в
зависимости от конкретного workflow.

`static/favicon`, `static/icons` и `static/uploads` не следует объединять или
переименовывать без отдельной задачи: у этих директорий разные назначения и
разный риск для существующих ссылок.

## Директория scripts

`scripts/` содержит вспомогательные скрипты разработки. Сейчас основным
скриптом является `scripts/check_i18n.py`, который проверяет, что ключи
`data-i18n` из HTML-шаблонов зарегистрированы в `static/js/i18n.js`.

Назначение и правила добавления новых скриптов описаны в `scripts/README.md`.

## Директория alembic

`alembic/` содержит миграции базы данных:

- `alembic/env.py` - окружение Alembic.
- `alembic/script.py.mako` - шаблон миграции.
- `alembic/versions/` - файлы миграций.
- `alembic.ini` - корневая конфигурация Alembic.

Миграции находятся только в `alembic/versions/`. Историю существующих миграций не
следует переписывать без отдельной причины и проверки окружений.

Историю миграций не нужно переписывать задним числом. Даже если в истории есть
похожие миграции, их не следует объединять после применения в окружениях. Любые
новые изменения схемы БД должны оформляться новой миграцией.

## Директория config

`config/` содержит настройки окружения:

- `config/.env` - локальные или текущие переменные окружения.
- `config/.env.example` - основной пример переменных окружения для локального
  запуска и документирования обязательных ключей.
- `config/.env.production` - production-oriented пример или конфигурация для
  production/local deployment-подхода.

`app/config.py` сначала пытается загрузить `config/.env`, затем fallback-ит на
корневой `.env`, если файл в `config/` отсутствует.

Логику загрузки env не следует менять без отдельной задачи: она влияет на запуск
приложения в разных окружениях и на ожидания deployment-процесса.

## Runtime и загружаемые данные

- `data/logs/` - место для логов.
- `data/backups/` - место для backup-файлов или заглушек под них.
- `static/uploads/` - пользовательские загрузки, которые отдаются через
  `/static`.
- `static/uploads/courses/`, `group_avatars/`, `group_homework/`,
  `group_materials/`, `materials/`, `videos/` - тематические подпапки загрузок.

Эти директории могут содержать runtime-файлы и не всегда отражают исходный код
приложения.

Часть media workflows использует локальные пути внутри `static/uploads/`, а часть
может отправлять файлы или изображения в Cloudinary через helpers в `app/utils`
и соответствующие роутеры. Не стоит смешивать локальную upload-логику и
Cloudinary-логику без отдельной задачи: у них разные ожидания по хранению,
ссылкам и удалению файлов.

## Где искать важные части

- Главная страница: `main.py` route `/` и `templates/pages/index.html`.
- Каталог и страницы курсов: `app/routers/courses.py`,
  `templates/courses/`.
- Кабинеты: `app/routers/users.py`, `templates/dashboard/`.
- Группы: `app/routers/groups.py`, `templates/groups/`.
- Организации: `app/routers/organization.py`, `templates/organization/`.
- Админка: `app/routers/admin.py`, `templates/admin/`.
- Переводы: `static/js/i18n.js`.
- Миграции: `alembic/versions/`.
- Настройки окружения: `config/.env*` и `app/config.py`.
- Загрузки пользователей: `static/uploads/` и Cloudinary-related helpers.

## Правила дальнейшего развития проекта

Эти рекомендации описывают желательное направление развития и не требуют
немедленного рефакторинга:

- Новые доменные модули желательно держать отдельно от роутеров, например в
  будущем слое `app/services` или в явно названных доменных модулях.
- Новые доменные функции не следует автоматически добавлять в `routers`: роутеры
  по возможности должны оставаться HTTP-слоем.
- `utils` желательно использовать только для технических функций: безопасность,
  загрузки, CSRF, форматирование, интеграционные helpers без собственной
  бизнес-ответственности.
- Крупные роутеры не стоит увеличивать без необходимости. Если новый workflow
  самостоятельный, лучше выделять его в отдельный роутер или сервисный модуль.
- Роутеры по возможности должны оставаться HTTP-слоем: принять запрос, проверить
  доступ, вызвать доменную операцию, вернуть response или template.
- Если появляется новая сложная доменная логика, предпочтительное место для нее
  - будущий `app/services`, а не расширение существующих крупных роутеров.
- Старый код не следует переносить массово без отдельной задачи и отдельной
  проверки поведения.
- При добавлении новых шаблонов стоит сохранять доменную группировку внутри
  `templates/`.
- При добавлении новых пользовательских загрузок нужно явно выбрать место
  хранения: `static/uploads/...` или внешнее хранилище, и использовать
  существующие upload helpers.
- При добавлении новых переводов нужно обновлять `static/js/i18n.js` и проверять
  ключи через `scripts/check_i18n.py`.
